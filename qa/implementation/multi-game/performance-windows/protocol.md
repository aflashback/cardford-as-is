# Native Windows performance protocol — frozen before measurement

Protocol `windows-replay-1`, 6 October 2026. This is a local compatibility/replay experiment, not application capacity, strategy, hosted service or language-wide evidence. The original M02A evidence is immutable. The current TypeScript app remains authoritative.

## Work and trust boundaries

The common workload derives only from the immutable original M02 fixture and original checkpoint expectations: 419 recorded transitions, 422 checkpoints (210 Spades Solo, 210 Spades Partners, two opening Hearts checkpoints), all four actor observations, public views and complete candidate IDs. Six complete Spades hands and only Hearts opening/pass are represented. Actual initial state JSON and command JSON strings are written once from the original oracle; both measured optimized workers consume identical UTF-8 strings. Seeds are not substituted for saved deals. No policy evaluation/provider call is performed.

Three variants are retained: historical Go JSON facade (`legacy-go`), optimized Go snapshots (`native-go`), and current Node reducers with matched checkpoint/output boundaries (`node`). Legacy Go keeps `Executor.Replay` unchanged, including its repeated validation/projection and internal frame serialization; its initial creation uses the same original configuration/deal. It is an implementation baseline, explicitly **not equal internal work**. The two optimized variants open and validate the same initial raw state each job, parse each recorded command once at the command boundary, apply one transition, validate each resulting checkpoint once at the game-state boundary, create one observation per seat, derive its public view/candidate IDs, and emit one full frame. Internal implementation-specific checks remain separately described; a semantic boundary count does not assert identical machine operations.

Every variant validates each serialized public `GameView` once at the harness output boundary. Go validates bytes through the strict public validator; Node parses those emitted bytes and calls the actual generated Ajv validator. The strict Go duplicate/surrogate policy remains; the positive corpus carries neither case. No invalid-input guarantee is removed to improve timings. Optimized variants serialize each complete frame exactly once. Serialized state, observation and view bytes are recorded; a raw SHA-256 stream of emitted complete frames is computed once. Raw serialization hashes may differ because object member order differs; exact per-checkpoint semantic hashes must match the frozen original expectations. Equal output size alone is never described as equal work.

An **untimed verification run** checks all 422 original state, observation, legal-action, candidate-ID and public-view hashes for each variant before measurements. The timed jobs retain schema checks and resource bounds but omit this multi-hash oracle traversal. Tests, correctness verification, profiles and timings have separate labels/artifacts.

### Remaining differences inside the matched boundaries

Counters named `checkpointValidations`, `initialStateDecodes`, `observations` and `*Serializations` count the declared job boundary calls and emitted values. They do not count every internal traversal, nested serializer, allocation or reducer check. In particular, the current Node saved-state reader is more expensive internally than a single semantic state assertion. The following are source-derived counts for the 420 Spades checkpoints and 418 Spades transitions only; the two Hearts checkpoints remain part of the complete measured workload.

| Internal operation | Current Node facade | Native Go snapshots |
| --- | ---: | ---: |
| Full game-state semantic assertion | 840 (`fromV1Spades` and then `spadesStateCodec.parse`) | 420 (initial import plus each transition) |
| Complete `json()` copying traversal in the saved-state reader | 2,520 (six per checkpoint) | Not this algorithm |
| Complete `structuredClone` in that reader | 840 (two per checkpoint) | Not this algorithm |
| Reducer state copies | 418 V1-to-native projections, 418 native reducer clones and 418 native-to-V1 projections | 418 explicit typed clones |
| Additional private-state projection for observation | 1,680 V1-to-native projections (four per checkpoint) | Zero; the typed snapshot is already native |

Node additionally reconstructs and freezes each parsed V1 state, validates individual events, and uses nested canonicalization for completed-trick checks. Those checks are preserved, as are Go's strict import/command parsing, validation and admission/cancellation checks. Public output validation uses Ajv versus Go's JSON Schema implementation; matching its boundary and positive result does not imply identical cost or universal invalid-input parity. The positive replay corpus contains no duplicate members or unpaired surrogates. Optimized Go versus current Node therefore compares these implementations under the same external replay/output obligations, **not equal internal algorithms or intrinsic language speed**. The legacy Go variant additionally retains its known repeated private decoding. No internal Node reader optimization or application route switch is made by this benchmark.

## Environment and timing

Both runtimes must be native Windows x64 on the same machine and repository working directory: Node `v24.19.0` and supported previous Go release line `go1.26.8`. The native Go path defaults to `.local/windows-tools/go1.26.8/go/bin/go.exe`; its version and binary hash are recorded. The integrator's exact-original-source control at `064001a` passed three CPU-profiler runs with Go 1.26.8, whereas three Go 1.27.1 CPU-profiler runs crashed in the Windows runtime. This selects a working stable toolchain for this experiment; it does not attribute ordinary replay failures or all Go 1.27.1 behavior to that defect. Earlier 1.27.1 evidence remains historical. The driver fails for another OS/version/architecture unless an explicit version/path override defines a separately identified experiment. It never invokes WSL, containers, `go run`, race instrumentation or a profiler during a timed run. Go is built once using the release compiler defaults before measurements. Binary/source/workload/protocol hashes are captured. No source files may change during the final run. The driver hashes the relevant repository source tree, including the Node runtime sources, rather than only the Go side.

Input files are read **once per child process**, outside all job timings. Input reading/decoding is reported separately. Each measured child performs three complete warmups; warmup one is recorded as `coldJob`, then one measured warm job. Six independent process repetitions use all six permutations of the three runtime variants, executing sequentially. This avoids always assigning the same implementation the first/last position. No other benchmark, compiler, profiler or test process may run concurrently. This controls sequence bias but is not a controlled hardware laboratory or broad load campaign.

The parent records whole child-process wall time, the child reports setup/input preparation, first-job and warm-job wall/CPU. Process launch/exit/loader residual is labeled as such; it is not treated as a pure language initialization measurement. Node dynamic-import time and Go pre-main initialization differ and are not silently folded into warm throughput. A separate process is used for each repetition, and every child has equal warmup counts. The first job uses a warm OS file cache if prior processes touched the file; it is not called a cold-disk benchmark.

CPU is whole-process user/kernel time from Windows `GetProcessTimes`; Node's `process.cpuUsage` uses the corresponding native process accounting. Memory is **process lifetime peak working set**, bytes/1024, from Windows `GetProcessMemoryInfo.PeakWorkingSetSize`; Node `process.resourceUsage().maxRSS` uses that same Windows field. This includes imports, input preparation, warmups and runtime heap behavior. It is not per-job live heap, retained application state or directly comparable with Unix RSS definitions. Windows process counters are described in the [libuv implementation](https://github.com/libuv/libuv/blob/v1.x/src/win/util.c).

Report each sample, median/range and CPU/working-set values. Six samples cannot establish a production p95/SLO. The old 10-second/256-MiB local correctness budgets are historical reference values, not new architecture acceptance criteria. No forced GC is inserted into timed jobs.

## Profiles and decisions

CPU/alloc profiles run in separate processes after baseline correctness. Go `runtime/pprof` CPU capture covers three jobs after three unprofiled warmups, using default allocation sampling. A separate allocation-only process captures one cold job with `MemProfileRate=1` after input preparation; its cumulative allocation profile includes schema initialization. CPU and full allocation tracing are never combined. Optional Node `--cpu-prof` captures the whole process, including imports, three warmups and three jobs; initialization and warm stacks must be distinguished when reading it. Profile counters identify private parsing, reflection, allocation, semantic validation, projection, serialization and hashing. The source-level baseline audit predicts 5,878 Spades state decodes, 6,298 Spades semantic validations, twice-per-frame serialization and repeated projection; actual profile evidence must substantiate how much time those costs consume.

Only measured, necessary fixes to redundant boundary crossing, serialization or I/O are justified by this experiment. Preserve closed-object checks, private-state validation, actor visibility, output validation, byte budgets, cancellation/admission and all original checkpoint hashes. Keep typed validated state within a job and serialize at real boundaries; do not globally cache untrusted/mutable state. Native PostgreSQL save/reload tests are separate root-owned end-to-end correctness work. The replay timing excludes network/SQL/transactions, full history, billing and policy execution; it cannot accept full application performance or choose a language winner.
