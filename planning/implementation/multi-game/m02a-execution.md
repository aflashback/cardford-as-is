## Finite limits and cancellation

These are compatibility-harness limits, not the full service executor or strategy budgets. One replay permits at most **256 commands**, **1 MiB** of conservatively counted input, **256 KiB** of private state per checkpoint and **512 KiB** per complete emitted frame (all selected actors included). Reserve the command count before dispatch; cap input and emitted sizes and check cancellation before each transition and projection. These are not reservations for every intermediate allocation. Admission has **2 active slots and no waiting queue** per executor; overflow rejects without starting work. HTTP test requests permit **16 KiB**, one command, a **2 second** context deadline and two slots per handler. PostgreSQL uses at most **2 connections** per test store, a **2 second** context deadline and compare-and-swap publication after computation. No connection is held during game work. M04/M05 must install shared service-wide admission; constructing multiple harness instances is not a global capacity control.

Cancellation before publication prevents a write. Cancellation after accepted publication cannot promise rollback; this slice does not implement durable command reconciliation. Process RSS is measured, not hard-limited by these logical byte bounds. Individual module calls are synchronous; cancellation is cooperative between bounded calls. Hard CPU/memory containment and complete sampler/fact/search budgets remain M05. Target: each bounded correctness replay finishes within **10 seconds** and **256 MiB observed process RSS** on the recorded machine; HTTP/database fixtures each finish within the stated deadline. Record failures before changing any target.

## Acceptance and non-activation

Preserve UTF-16 capture hashes and legacy digest algorithms on their documented supported domains. Test invalid JSON, private fields, unsupported pins, missing/null values, lost revision races, owner denial, cancellation, saturation and PostgreSQL save/reload. Preserve the six canonical SQL migration checksums; the test store uses a random throwaway schema inside a database whose name ends `_test`, never the live application tables.

It does not establish hosted identity, billing, recovery, full historical readers or prepared analysis parity. No executable production server is introduced. A passing result permits M03 durable record design/implementation; it does not switch an existing session to Go. Human review, fresh Jev comparisons and deployment remain separate deferred gates.

## Migration packaging freeze

`web/server/records/migrations/001-local-platform.sql` through `006-preparation-attempts.sql` are the sole canonical migration files. The M02A verification report records their individual SHA-256 hashes. M03 packaging must consume these same bytes, using a generated embedded bundle or explicit build copy checked against that manifest; generated copies are never editable sources. Record/check applied migration hashes and reject a mismatch. New schema work starts with a forward `007` migration; never renumber, rewrite or regenerate the existing six. M02A uses one disposable schema/table in the existing `_test` database and does not install replacement platform records or run migrations against saved user games.

## Benchmark correction

The first comparison attempt called the M02 parity harness, which repeatedly serialized and validated V2 documents for each projection. That does not represent the optimized current app path. It was stopped before accepting or publishing timing conclusions. The final comparator calls the installed `game/index.ts` facade and game-owned observations, with the current `validateStoredGameState` boundary once per checkpoint. Both sides replay the same recorded choices, emit the same complete checkpoint work and include serialization. Go currently revalidates its JSON facade inputs more often; this conservative slice is not a controlled language-only speed test. Limits and policy/work inputs were not relaxed to obtain the final result.
